## Context

动机和已确认边界见 [proposal.md](proposal.md)。现有入口把 Review 排在验证前, 参考文档还显式允许 Review 先于部署; 既有部署、测试和交付规则可复用, 不需要新增执行框架。

## Goals / Non-Goals

目标是以统一顺序连接九份现有文档, 让当前 Patch 的用例、部署版本、真实结果、审查与最终本地门禁可逐项核对。非目标是实现新的测试平台、扩大部署或 Git 权限, 或在本次文档变更中执行真实业务验证。

## Decisions

1. `SKILL.md` 保持唯一开发主顺序。`backend-development.md`、README 与 delivery 只串联, 测试文档分别细化目标栈和双轨用例, runtime 文档提供版本与部署验收证据。沿原段落改写, 不平行维护另一套流程。
2. 产品文档在需求确认后形成验收初稿, 实现后依据确认行为和实际代码补齐自动化及人工用例。模板统一记录测试类型、入口或步骤、版本、真实执行者、状态和证据, 前后端按实际影响适用; 不新增真人全量重复执行或签字制度。随 Patch 交付的产品文档、tasks 和验收报告在首轮正式 Review 前完成当前环境验收结果及真实稳定动态证据入口并冻结。冻结后的 Review/最终本地门禁等动态结果记录在目标 Patch 外的已有交付说明或本次当前会话交付记录中, 绑定明确基线和冻结后确定的完整 Patch 版本/指纹; 文档通过预先确定的入口引用, 不为回填结果修改冻结文件, 最终对外说明提供实际结果和入口。确需修改文档时仍清零重走闭环, 不豁免文档变化。
3. `code-review.md` 定义三个干净会话的完整审查、交叉核验、记录和清零规则。开发正式 Review 接收已通过的当前环境验收证据; 普通只读 Review 不要求为此部署, 审查 Agent 始终只读。容量和模型服从会话现状, 不写工具或模型名。
4. 同一未变 Patch 可复用持续有效的环境验收证据, 三轮只重建审查会话。Review 或最后本地门禁失败引起修复时, 更新用例、重新部署验收, 再从零完成三轮 Review。与独立 CI 任务的三轮修复上限分开, 不以修复轮数抵扣通过轮数。
5. 最后 Review 后运行既有本地门禁, 保留前置必要快速检查但不作为最终结果。Python 沿用真实 tox/解释器约束和项目覆盖率门槛, 其他栈沿用对应入口; 不适用与失败/未执行分开记录。delivery 再核对完整暂存版本和独立 Git 授权。

## Risks / Trade-offs

- 环境或工具缺失会使开发交付链停在真实验收前 -> 明确未完成项, 暂停依赖 Review/提交, 不用 Mock 或静态检查替代。
- Agent 结果容易被误写为真人验收 -> 模板将类型、真实执行者、状态分开, 必验人工项缺结果不能全通过。
- 后续修复或暂存范围变化使旧证据失效 -> Patch 变化清零, 重走验收和审查, 提交前核对基线与最终完整暂存内容。
- 最终结果回填仓内文档会再次改变已审 Patch -> 首轮 Review 前冻结文档及真实入口, 后续结果在入口对应的 Patch 外记录, 对同一基线和完整版本核验, 不把任务勾选或待执行状态当作最终通过。
- 文档检查不能证明模型实际执行流程 -> 本次仅记录静态验证, 最终干净复审和验收由主会话在冻结后发起并据实记录, 仓内准备/对账项勾选不表示最终已经通过。

## Validation

仅检查受影响文档的新增行标点、frontmatter、内部链接、diff 空白及 OpenSpec strict, 并静态走查正常路径、E2E 失败、Review 修复、最终本地检查失败、权限/能力缺失、单端不适用和只读 Review, 以及仓内产品文档冻结后引用外部最终结果而保持同一 Patch 的成功路径。保留原有部署授权、备份恢复、Jira/Git 门禁及 self-contained 约束; 不执行真实业务部署和测试, 不 Archive。
