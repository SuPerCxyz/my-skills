## Context

动机和已确认边界见 [proposal.md](proposal.md). 沿用已有环境验收、三轮 Review 和最终本地门禁, 就地修复阶段集合、Jira 核验、已有提交交付及覆盖判据的衔接, 不新增执行框架.

## Goals / Non-Goals

目标是以统一顺序连接九份 workflow 文档及必要 CI/Git 入口, 让当前 Patch 的用例、部署版本、真实结果、审查、本地门禁和 Jira 交付结果可逐项核对. 非目标是实现新的测试平台、改变非 EasyStack 交付、扩大部署/Git/Jira 权限, 或在本次文档变更中执行真实业务验证.

## Decisions

1. `SKILL.md` 保持唯一开发主顺序. Review 前必验集合仅包含适用的环境 E2E、人工项和业务终态验收; Review 后最终本地门禁单列, 未执行不反向阻塞正式 Review. 其他 workflow 文档只同步该定义或细化对应阶段, 不平行维护另一套流程.
2. 产品文档在需求确认后形成验收初稿, 实现后依据确认行为和实际代码补齐自动化及人工用例。模板统一记录测试类型、入口或步骤、版本、真实执行者、状态和证据, 前后端按实际影响适用; 不新增真人全量重复执行或签字制度。随 Patch 交付的产品文档、tasks 和验收报告在首轮正式 Review 前完成当前环境验收结果及真实稳定动态证据入口并冻结。冻结后的 Review/最终本地门禁等动态结果记录在目标 Patch 外的已有交付说明或本次当前会话交付记录中, 绑定明确基线和冻结后确定的完整 Patch 版本/指纹; 文档通过预先确定的入口引用, 不为回填结果修改冻结文件, 最终对外说明提供实际结果和入口。确需修改文档时仍清零重走闭环, 不豁免文档变化。
3. `code-review.md` 定义三个干净会话的完整审查、交叉核验、记录和清零规则. 开发正式 Review 接收已通过的当前环境验收证据; 普通只读 Review 不要求为此部署, 审查 Agent 始终只读. Jira 的站点/项目、真实编号、存在性和范围对应关系尚未可信核实时保留入口门禁; 已核实但实时详情或讨论不可读时, 普通 Review 可基于现有证据继续, 关键缺口使用 NEEDS VERIFICATION. 容量和模型服从会话现状, 不写工具或模型名.
4. 同一未变 Patch 可复用持续有效的环境验收证据, 三轮只重建审查会话。Review 或最后本地门禁失败引起修复时, 更新用例、重新部署验收, 再从零完成三轮 Review。与独立 CI 任务的三轮修复上限分开, 不以修复轮数抵扣通过轮数。
5. 最后 Review 后运行既有本地门禁, 保留前置必要快速检查但不作为最终结果. Python 沿用真实 tox/解释器约束和项目覆盖率门槛, 首次验证与失败修复均额外核验完整本次 diff 的新增/修改可执行行及相关分支无 mis/par. 覆盖范围含确认的 committed/staged/unstaged 与未跟踪新源码, 保留既有排除规则并列明影响, 不追补无关历史缺口或新增豁免. 缺报告/测量不当作无缺口; tox 成功、增量门禁失败或未验证分别报告. CI skill 的普通入口、auto-fix 和 coverage 共用此判据; 仅验证不自动修复. 其他栈沿用对应入口.
6. delivery 在 commit/amend 前检查完整最终暂存 Patch, 在直接上传已有提交前检查完整待发送提交范围, 都与对应基线和同版环境验收、三轮 Review、最后 Review 后本地门禁证据对账. 有效证据复用, 缺失或变化则暂停依赖动作并在授权内补足, 不自动修改提交、部署或扩大权限. git-delivery 仅在已识别的 EasyStack 分支引用本规则, 不推广到个人或其他公司项目.
7. Review Links 的详细规则维护在 delivery 上传后对账段落, 入口与 README 仅同步完成条件. 对适用公司 Bug 规范的 Jira, 从真实上传/远端结果核对仓库、目标分支/版本与 Change URL 集合, 在已有内容基础上按有效字段授权合并、去重并回读; 不预填未来 URL, 不把 Git 或 Conclusion 授权扩为此字段权限. 已准确覆盖只核实, 失败/未知先回读查证, 未完成单独报告并保留完整交付缺口.

## Risks / Trade-offs

- 环境或工具缺失会使开发交付链停在真实验收前 -> 明确未完成项, 暂停依赖 Review/提交, 不用 Mock 或静态检查替代。
- Agent 结果容易被误写为真人验收 -> 模板将类型、真实执行者、状态分开, 必验人工项缺结果不能全通过。
- 后续修复或暂存范围变化使旧证据失效 -> Patch 变化清零, 重走验收和审查, 提交前核对基线与最终完整暂存内容。
- 最终结果回填仓内文档会再次改变已审 Patch -> 首轮 Review 前冻结文档及真实入口, 后续结果在入口对应的 Patch 外记录, 对同一基线和完整版本核验, 不把任务勾选或待执行状态当作最终通过。
- 文档检查不能证明模型实际执行流程 -> 本次仅记录静态验证, 最终干净复审和验收由主会话在冻结后发起并据实记录, 仓内准备/对账项勾选不表示最终已经通过。
- 首次普通 CI 可能由原来的 tox 成功转为增量覆盖门禁未通过 -> 本轮已明确确认收紧判据, 命令事实与质量结论分开, 不擅自修复或放宽覆盖配置.
- 上传完成但 Review Links 字段无权限 -> 保留上传成功事实, 提供合并草稿并报告 Jira 交付记录未完成, 不自动重传或越权补写.

## Validation

仅检查受影响文档的格式/新增行标点、frontmatter、内部链接与锚点、文件索引、diff 空白及 OpenSpec strict, 并静态走查阶段集合、失败修复、已有提交同版证据复用/失效、多仓/版本 Review Links 合并/权限/未知结果、首次 CI 的增量缺口/历史缺口/缺报告、Jira 未核实/详情不可读和纯只读入口. 保留原有部署授权、备份恢复、冻结文档外置证据及 self-contained 约束; 不执行真实业务部署和测试, 不 Archive.
