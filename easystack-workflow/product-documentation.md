# Product Documentation

## Purpose And Timing 用途与时点

每次新增功能或修改都生成或更新产品文档, 服务产品使用、行为理解和验收. 在需求确认后
形成验收目标初稿, 以确认的行为清单为范围; 修改代码后依据需求与实际实现补齐适用的
前后端及必要跨层测试, 同时提供可重复自动化 E2E 入口/脚本/断言和可人工执行的前置、步骤、
预期. 未涉及的一端说明不适用, 不生成无关用例. 验证前呈现完整测试顺序, 首轮正式 Review
冻结前完成需求、用例和当前环境验收的真实执行者、步骤、版本、状态、结果及未验证项对账.
纯内部修改如无可见行为变化, 说明影响和边界, 不虚构用户功能.

随 Patch 交付的产品文档、tasks 和验收报告均纳入完整目标 Patch, 首轮正式 Review 前冻结.
冻结前在文档中确定真实稳定的动态证据入口, 可使用目标 Patch 之外的已有交付说明或本次
当前会话交付记录, 不编造 URL 或平台. 冻结后的每轮 Review、最终本地门禁及后续验收状态
仅在该入口的外部记录中更新, 绑定明确基线和冻结后确定的完整 Patch 版本/指纹; 文档通过
已确定入口引用实际结果, 不要求最后检查后回填冻结文件, 也不提前写为通过. 最终对外说明
提供实际结果和证据入口. 确需修改任何目标文档时, 仍清零并按原规则重走验收和审查闭环,
不将文档排除在 Patch 之外或豁免变更清零.

优先使用目标项目已有的产品文档目录和格式. 项目没有适用位置时, 使用
`docs/product/<change-name>.md`. 同一变更可在一个文档中覆盖多个功能, 不强制每功能单独成文,
也不强制修改 `rainbow-doc`. 不补写与本次变更无关的历史功能. 产品文档描述产品行为和验收;
有效 OpenSpec/Plan 继续承担设计和实施规划, 两者相互引用, 不另建同用途规划文档.

## Required Content 必需内容

文档逐项对应本次新增或修改, 建议使用稳定编号, 至少说明:

- 功能列表及本次变化, 含适用入口和用户/调用方可见效果; 无可见行为变化时写明影响.
- 功能边界、权限或适用条件, 以及明确不覆盖的相邻行为.
- 适用的异常场景和预期反馈、状态、恢复或限制.
- 测试内容, 覆盖确认行为的成功、边界、异常及必要恢复路径.
- 每项测试的类型(自动化 E2E、人工用例或本地门禁)、本次是否必验、依赖/前置条件、
  可复跑入口/脚本及断言或人工步骤、预期结果, 关联功能编号与执行顺序.
- Patch、产物与环境运行版本的对应关系, 冻结前已有用例的真实执行者、状态、结果和证据;
  后续 Review/最终本地门禁等动态结果通过上述真实入口引用, 外部记录绑定基线和完整 Patch 版本/指纹.
  Agent 操作不得记为真人, 未执行不记通过; 不新增真人全量重复执行或签字要求,
  但本次必验人工项未执行不得全通过.

前端改动复用上述内容形成用户查看验收清单: 环境 URL 与实际部署版本、页面入口、改动
所在位置、查看操作、预期结果, 以及风险和未验证项. 环境或部署未完成时明确标记,
不提供猜测地址或旧版本冒充本次结果. 无可见变化时说明实际影响与验证方式,
不虚构界面改动. 最终回复直接呈现这份简短清单, 不仅提供代码文件或产品文档链接.

## Test Order 测试顺序

验证前先整理并呈现完整测试顺序, 再开始执行. 按功能依赖和业务生命周期排序: 若 A 依赖 B,
先完成 B 的测试, 再执行 A 并复用仍有效的资源和结果. 共享前置条件集中准备, 不因去重而删掉
必要的边界或异常覆盖. 异常及破坏场景安排在不影响后续前提的位置; 必要复验注明原因.

前置步骤失败时, 将依赖它的项目标记为阻塞并说明原因, 不假执行或记为通过. 清理顺序按依赖
关系反向安排, 且遵循用户授权及本目录 `backend-testing.md` / `frontend-testing.md` 的资源操作规则; 本文档不扩大环境操作或删除权限.
开发交付顺序统一见 [SKILL.md](SKILL.md#development-flow-开发流程): 环境部署和必验项
真实通过后再正式 Review, 三轮无问题后运行同版最终本地门禁. Review 或最终检查失败引起
修复时同步用例和版本, 重部署验收、清零并重做三轮 Review, 再执行最终检查. 同版环境与
证据有效且未改码时可复用结果, 不机械重复部署; 构建前快速检查不能替代最终门禁.

## Template 模板

```markdown
# <变更名称>

## Scope 范围

- 依据: <Requirement Review / OpenSpec / Plan 链接>
- 版本或适用条件: <项目版本、角色、租户或入口>
- 验收环境: <适用前端 URL 或后端 API/CLI 入口, Patch/产物/运行版本对应关系, 未部署原因>
- 适用端: <受影响前端/后端/跨层路径, 未涉及端的不适用依据>
- 本次边界: <涵盖与不涵盖的行为>
- 动态证据入口: <冻结前已核实的 Patch 外已有交付说明位置, 或本次当前会话交付记录; 冻结后由该入口绑定基线和完整 Patch 版本/指纹>

## Features 功能

| 编号 | 功能或修改 | 入口/改动位置 | 用户/调用方效果 | 异常与边界 |
|------|------------|---------------|-----------------|------------|
| F1 | 前置功能 B | B 的页面入口和位置或调用入口 | B 可独立完成 | B 的边界与失败反馈 |
| F2 | 依赖 B 的功能 A | A 的页面入口和位置或调用入口 | A 使用 B 产生的有效结果 | A 的边界与失败反馈 |

## Test Plan 测试计划

| 顺序 | 功能 | 类型/本次是否必验 | 依赖/前置条件 | 自动化入口/脚本及断言或人工步骤 | 预期结果 |
|------|------|-------------------|---------------|--------------------------------|----------|
| T1 | F1 | 自动化 E2E/<确认范围> | 集中准备 B 的前置 | <可复跑命令/脚本, 验证状态与实际业务效果的断言> | B 完成并产生可复用结果 |
| T2 | F2 | 人工用例/<确认范围> | 复用 T1 的有效结果 | 1. <从实际页面或 API/CLI 入口操作 A>. 2. <核对结果>. | A 完成并反馈预期结果 |
| T3 | <目标 Patch> | 最终本地门禁/是 | 同版环境验收与三轮 Review 通过 | <项目已有 pep8/coverage 或其他栈对应入口及配置阈值> | 本地门禁全部通过 |

## Results 结果

| 顺序 | 被测/环境版本 | 真实执行者 | 状态 | 实际结果/证据 | 未验证/阻塞/不适用依据 |
|------|---------------|------------|------|---------------|------------------------|
| T1 | <Patch/产物/运行版本> | <Agent/实际工具入口> | <通过/失败/阻塞/未执行> | <真实命令、断言与结果证据> | <原因或无> |
| T2 | <同版对应关系> | <真人标识或实际 Agent, 未执行不填> | <通过/失败/阻塞/未执行> | <真实步骤与业务终态证据> | <原因或无> |

T3 与三轮 Review: <实际执行者、版本、状态、命令和结果见上述动态证据入口, 不回填冻结文件; 未有真实结果不得视为通过>
清理: <逆依赖顺序、对象状态及授权范围内的结果>
冻结前验收状态: <环境部署、E2E、必验人工项分别记录; 三轮 Review、最终本地门禁及后续实际状态见动态证据入口>
冻结前前端验收状态(仅前端改动适用, 其他任务不适用): <构建、部署、实际页面版本和业务/视觉验证各自结果, 风险与未验证项>
```

若 T2 或其他后续操作会改变前序结果的有效性, 说明原因并安排必要复验.

## Completion 对账

冻结前核对功能编号、测试顺序、实际实现和当前环境验收结果一致; 完成失败、阻塞、未验证项
及必要复验的对账. 冻结后按上文规则在动态证据入口核对后续实际结果, 不无条件回写目标文档;
最终交付说明提供实际结果、证据入口和产品文档链接. 用例类型与真实执行者分开记录; Agent 代执行不得冒充
真人, 本次明确要求真人执行的必验项在真人完成前保持未完成. 未执行的计划步骤不得写成验证通过.
清理未获授权时记录对象、
状态和后续建议, 不自行删除.
前端查看清单在冻结前与实际部署版本和结果对齐; 后续实际状态及剩余项在动态证据入口和
最终说明中报告, 已部署与已验收分别表述, 未完成时不声称完整交付.
