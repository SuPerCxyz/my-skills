# Release Test Execution

## Release Scope 发布范围

- 记录待测版本或构建、目标环境、变更范围、计划或单用例来源及执行授权。
- 从指定的 MeterSphere 计划、本地用例及本轮变更和缺陷回归记录发现候选。按用例编号或稳定标识
  去重, 记录来源、纳入原因、覆盖的变更或风险, 以及跳过和未覆盖原因。
- 使用当前来源的原始步骤、预期和标识。查询 MeterSphere 时, 按实际可用能力读取对应
  计划和用例, 已加载 `metersphere` 时复用其查询流程。本地用例保留文件路径及编号。
- 批量任务开测前按 [执行汇总](execution-summary.md) 建立计划和全部状态。单条用例建立
  对应报告, 按本轮范围执行。

## Case Review 用例审查

1. 核对原始前置、操作入口、参数、顺序、条件分支和每步预期。发现缺失、冲突或无法判断的
   业务断言时记录原文、影响和建议修订。
2. 将长步骤拆成可执行子步骤, 保持原始编号、被测入口和预期, 并关联实际操作。会改变
   业务断言、入口或关键参数的调整须获确认后纳入执行, 记录依据与差异。
3. 关键定义无法确定的用例记为 `case-issues`。整理建议单独留痕, 修改用例来源按已有授权。

## Case Preview 用例总览

在每条用例的首个操作前, 包括创建或调整用例所需的前置资源, 向用户展示用例编号、名称
和 [报告模板](#markdown-report-用例报告) 中的用例总览。列出原用例的前置条件, 按原始顺序
逐步列全操作与对应的预期结果, 保留参数及分支。批量或子 Agent 执行时, 主会话在相关用例
开测前发出总览。

## Execution Flow 执行流程

1. 读取、审查并展示本轮用例。仅审查时输出用例范围和问题清单。
2. 执行 Web 用例时, 通过当前客户端加载 `easystack-cloud-web-e2e`, 确认可用的浏览器
   能力和取证方法。缺少执行能力时记录受影响用例的阻塞, 继续可独立完成的审查。
3. 按 [环境预检](environment-intake.md) 核对版本、项目、账号、资源余量和授权, 并读取
   对应资源域的原子操作。
4. 将用例编号、run id、目标项目、角色、资源身份或逻辑名映射、原始步骤、预期和证据
   要求交给执行层。按步骤逐段接收观察, 回读异步或不确定结果后再推进。
5. 使用 Web E2E 的 `patterns.md` 中的原子操作约定, 包括 `ok`、`terminal`、
   `submitted`、`id`、`status`、`url` 和 `message`。附上实际证据路径、最后观察和未确认
   资源。应用用例预期得到步骤和用例结论。
6. 输出用例报告及资源清单, 汇总覆盖与阻塞, 复测关联原运行和新证据。已有项目准出条件时
   据此列出发布阻断项和仍需验证的项。

## Case Verdict 用例判定

- 操作状态代表产品实际观察。预期拒绝或预期失败的步骤以真实拒绝或失败状态和业务效果
  对照断言, 例如预期挂载失败时应核实实际失败及后续状态。
- 用例定义缺失、冲突或产品范围不符记为用例问题。环境、权限、依赖或执行手段不能完成
  断言时记为阻塞并记录原因。前置就绪且产品实际结果偏离原始预期时记录产品失败。
- 用户跳过、长耗时跳过和未执行在执行汇总说明原因。报告和汇总均保留未完成范围。

## Resource Handling 资源管理

- 显式要求优先。静态配置和页面默认值用于用例允许且已核实的选项。
- 每个独立用例新建唯一的测试资源, 使用 `<case-id>-<resource-type>-<runid>` 等名称。
  前置条件中的 `vm1` 或 `volume1` 等逻辑名映射为本轮对象, 同时记录逻辑名和实际名。
  仅在已明确授权复用指定资源时使用既有对象, 操作前回读项目、身份、状态和影响。
- 无法确认创建终态时记录 `unconfirmed_resources[]`、最后回读和恢复检查点, 按 Web E2E
  的有限核对和重试规则处理。中断或换执行者后先核对已发生的动作、资源和证据, 复用已确认
  成功的结果。用户取消时停止用例, 汇总已核实事实和未完成范围。
- 默认保留测试资源供验收。VM 资源或配额不足时, 该清理例外只涉及已授权的本任务测试 VM,
  记录名称、ID、原因和时间。其他清理按实际授权和目标范围执行, 开始前明确影响与顺序。
  Web 删除使用 Web E2E 的清理顺序和操作约定。缺少清理授权时写 `cleanup: recommended`。

## Permission Escalation 权限升级

- 按 [环境预检](environment-intake.md) 准备普通用户和管理员账号。默认以普通用户执行。
  管理员可按已授权范围进行项目配额、类型管理和测试前置操作, 准备完成后恢复用例角色。
- 涉及部门、项目、用户或配额时, 参见 [IAM 开通](iam-provisioning.md)。记录权限使用的
  对象、原因、变更前后值和实际回读结果。
- 后台查询用可用且已授权的能力。遇到角色权限验证, 保持用例要求的角色和预期。前置无法
  满足或后台认证失败时, 按阻塞判定并记录证据。

## Evidence Policy 证据规范

### Result Paths 结果目录

| 结论 | 结果目录 | 判定 |
|------|----------|------|
| 通过 | `pass/<编号>-<用例名称>/` | 实际结果符合用例预期 |
| 失败 | `fail/<编号>-<用例名称>/` | 前置满足, 实际产品结果与预期不符 |
| 阻塞 | `blocked/<编号>-<用例名称>/` | 环境、依赖或权限不足, 无法得出产品结论 |
| 用例问题 | `case-issues/<编号>-<用例名称>/` | 用例步骤、预期或输入参数缺失、冲突或与产品范围不符 |

结果根目录由任务指定, 缺省使用模板的 `evidence.result_dir`。每个用例结果目录包含
`<编号>.md`、`screenshots/` 和 `videos/`。记录实际取得的证据,
未执行相关步骤时在报告说明原因。结论变化时移动用例目录并同步更新 `resultDir`。
测试计划的跳过和未执行用例在 [执行汇总](execution-summary.md) 记录原因。

### Markdown Report 用例报告

- 报告开头记录用例编号与名称、执行时间、环境/项目、结论和原因。随后放入开测前展示的
  用例总览, 再按同一原始顺序记录实际执行明细。
- 主步骤使用 `## 步骤 01 <原始步骤标题>` 格式。需要拆分时, 实际执行步骤按
  `1.1`、`1.2` 编号, 第二个主步骤从 `2.1` 开始。每个步骤依次写实际执行步骤、
  实际结果、与预期对比和证据。
- 报告末尾先写创建资源清单及所需的清理说明, 再写整体录像。资源的身份与状态以回读为准。
- UI 步骤完成后立即截图。图注单独一行, 使用 `图 1-1`、`图 1-2` 的格式, 分别表示
  步骤序号和该步骤内的图序。图片使用独立左对齐的块, 统一显示宽度 960 px 并保持原比例。
  图片文件使用 `screenshots/<主步骤>.<图序>-<说明>.png`。
- 镜像元数据等后台专属证据, 进入已授权的后台只读查询对应资源详情。在所属步骤下
  注明查询对象、来源和时间, 用带语言标记的代码块粘贴脱敏后的实际输出。后台步骤可直接
  以查询输出作证, 同一步骤有 UI 交互时附上 UI 截图。

### Case Evidence 用例取证

- 页面步骤按 Web E2E 方法截图和录制, 并使用已验证可播放的成片。后台专属证据使用
  已授权的只读查询并脱敏, 以代码块贴在所属步骤。
- 在报告末尾的 `## 整体录像` 使用
  `<video src="videos/<编号>.webm" controls preload="metadata" width="960"></video>` 嵌入,
  下一段提供普通链接 `[打开录像](videos/<编号>.webm)`。推荐使用执行入口已验证的
  播放格式, 可在需要时使用同名 MP4 成片。确需分段时按操作顺序列出各段。
- 运行产物与状态仅写入本次结果目录。创建资源清单记录逻辑名、实际名称、类型、真实 ID、
  终态和保留或删除说明。全局 `test_report.json` 可放在结果根目录。
- 短段执行或恢复时记录最后确认的资源、步骤、证据和未确认终态, 便于回读核实。

## Long-Duration Cases 长耗时用例

- 阈值规则：单个用例/步骤预计 **≤1 小时**可以执行；预计 **>1 小时**默认跳过。
- 默认跳过：72 小时稳定性、性能基线、无限时 fio/压力、需要多日等待的用例。
- 只有用户在当前任务中明确要求时才执行超过 1 小时的用例；执行前确认窗口、资源和回滚方案。
- 默认窗口内接近 1 小时仍未完成时停止, 记录实际耗时和未完成步骤。经授权的长用例按确认窗口执行。
- 跳过的用例在报告中标记 `skipped (long_duration)`，不计入失败或通过率。

## MeterSphere Comment 模板

有明确回填授权时, 按核实的目标计划和用例记录结果与 comment。

```text
[执行结果] 通过/失败/阻塞/用例问题/跳过
[实际结果] ...
[资源] <name>(<id>) / <name>(<id>) ...
[环境] <产品/版本> / 项目 <project> / 类型 <actual>
[证据] <结果目录中的截图、后台证据所在步骤及成片相对路径>
[执行] <name> / <YYYY-MM-DD HH:MM>
```

- 先核对平台用例编号与本地编号。
- 平台不支持附件时写本地路径与文件名。
- 状态与 comment 同批次提交，不能只改状态。

## Retests And Summary 复测与汇总

按 [执行汇总](execution-summary.md) 保留全部用例和各次执行。复测记录新的 run id 或结果路径,
关联被复测的问题和原证据。汇总按最新有效结论表达状态, 保留历史结果和未覆盖原因。
